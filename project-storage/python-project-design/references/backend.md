# 后端与前端契约

## 服务归属与跨服务调用

- **划分服务** 按业务能力和规则变化的范围划分。把经常一起变化的流程留在一个服务；即使没有独立表，报表或工作流也可以有独立职责。规模小时，同一个应用进程内用若干模块就够了。
- **明确维护责任** 每张应用维护的表有一个服务负责它的结构、索引、约束和写入规则。项目统一管理迁移时，仍按服务标记或记录每项迁移的归属。共享连接池、会话与事务工具、配置和启动逻辑可集中放在 `system/` 或项目已有的基础设施模块。
- **约定模块入口** 一个服务的路由、业务操作、领域类型和表访问就近组织。以 `services/<domain>/` 为例，按复杂度选用 `routes.py`、`operations.py`、`models.py`、`tables.py` 和 `_helpers.py`。简单服务可用单文件，传输类型和领域类型确实分化时再拆开。
- **约定跨服务调用** 同一进程内可直接调用公开业务函数或已封装的表方法，例如 `activity.tables.list_entries(conn, user_id, period)`。涉及权限、状态迁移或多表业务规则的写入，调用拥有这些规则的业务入口。表方法负责参数绑定、查询执行和行映射。SQL 常量和私有辅助逻辑留在所属模块，调用方使用具名操作。
- **划清身份与权限** 账户或认证模块负责验证凭证、会话和可信身份。资源的所属服务负责该资源的访问规则。业务操作接收已验证的身份，并按资源规则判断权限。直接调用表方法的入口也要满足适用的访问条件。

例如工时项目可以这样标明归属。

| 服务 | 维护的数据与规则 | 公开能力与依赖 |
| --- | --- | --- |
| `accounts` | 用户、会话与身份验证 | 解析凭证并返回可信用户身份 |
| `activity` | 工时记录及其变更规则 | 提供记录查询和更正操作 |
| `reports` | 汇总和报表口径，可无自有表 | 按 `activity` 的访问规则查询允许读取的记录，再做聚合 |

一次读写操作的路径可以是：

```text
页面 → 前端调用器 → 路由解析输入和可信身份
    → 业务操作组织查询、规则判断和写入
    → 所属模块的公开表方法 → 响应
```

一个有名称的函数就可以是业务入口。操作已有消息类时，可以沿用 `plan(conn)`。构造请求或消息时保存输入，执行入口接收所需依赖并按顺序处理。路由负责传输校验和错误到 HTTP 的映射，业务操作根据可信身份做资源级授权。仅供后端复用的函数留在进程内。

## 数据库与事务

- 需要原子性的步骤共享连接和同一个事务，事务由能看到完整操作的调用边界管理。底层查询和写入方法沿用调用方的连接。同步项目可以用事务上下文管理器，已有异步驱动时沿用其异步上下文。
- 沿用已有数据库和迁移方式。新建 Web 应用需要共享的关系库时，PostgreSQL 是合适的默认选项。单机工具按部署和并发需求选型。使用绑定参数，约束和迁移随项目既有机制维护。

## 对齐前后端

共享传输集中维护。业务调用器按业务域组织，可以是函数，也可以沿用项目已有的请求类。用 HTTP 方法、稳定路径或明确的操作标识建立对应关系。一个公开端点应能追到它校验的输入、返回结构和业务操作。外部路由和契约标识随着接口兼容策略演进。

新建 JSON API 时可选 FastAPI 与 Pydantic，让请求和响应模型生成 OpenAPI。需要维护 TypeScript 契约时，可以使用 schema 生成类型或做契约检查。领域计算可以继续用标准库类型。保留有业务含义的前端调用器，由公共传输处理网络细节。
