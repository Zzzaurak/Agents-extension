# Python 项目设计

让读者能从入口找到业务规则、输入输出和实际的 I/O。已有项目沿用现有入口、工具链与接口行为。小脚本可以在单文件里完成，只有复杂度或复用需求增加时才拆模块。

## 建模与计算

- 计算显式接收业务数据和时间等参数，返回结果或新值。在入口或编排函数里读时钟、数据库、文件和网络。需要更新领域记录时，优先构造新值。
- 用生成器表达式、推导式、聚合或清晰的命名函数表达筛选和转换。多步计算可以保留有意义的阶段变量。批量写入、流式读取和带提前退出的流程可以用清晰的循环。
- 边界函数写清有意义的输入和返回类型。用 dataclass 表达有行为约束的业务记录，用枚举或联合类型表达有限状态。共享的值对象可用冻结 dataclass 和不可变字段。仅在容易混淆时区分不同种类的 ID。
- 区分合法缺失、预期的业务拒绝与基础设施故障。查询缺失可以返回 `T | None`。调用方需要分支处理的业务结果可以用联合类型，异常由能处理它的边界解释。

## 服务归属

- 先按业务能力划分服务，再明确每个服务拥有的规则和数据。每张由应用维护的表指定一个负责其结构和写入规则的服务。服务可以是同一进程里的 Python 模块，也可以只负责跨域编排。
- 跨服务调用走对方的公开业务操作或封装好的表方法。领域规则和授权由负责该规则的服务执行，SQL、行映射和私有辅助函数留在所属模块。已有模块结构优先，新项目可参考 `services/<domain>/`。

## 按任务采用

- API、数据库或全栈任务读 [后端与前端契约](references/backend.md)。新建或调整多个服务时，先列职责、所属数据、公开入口和调用方向，在项目说明中记录实际边界。
- CLI、批处理、报表或数据分析读 [脚本与数据工作流](references/data-workflows.md)，把解析、计算与输出组织成可单独验证的步骤。
- 规划新结构时列出主要入口、业务职责和必要的读写边界。功能较多时在项目 README 记录实际入口与模块的对应关系。局部修复沿用已有结构，修改涉及的契约和说明。
- 用项目已有的检查方式验证受影响的规则。纯计算验证代表性输入，外部边界按涉及的行为验证，例如查无数据和读写失败、事务回滚、输入输出字段。静态检查按项目现有配置运行。
